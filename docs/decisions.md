# 기획 원칙과 결정

사용자의 명시적 방향과 적용 제안을 구분한다. 근거일: 2026-11-08.

## D-001 기획과 사용자 경험을 먼저 구체화한다

**사용자 방향:** “프로젝트 기획 보고서, 제품 시안과 사용자 관점의 UI/UX, 그리고 사용자 가이드를 우선으로 뽑아내고 어느정도 완성한 후에 실제 제품 구현을 진행하고 싶어.”

**적용:** 세 산출물을 연결해 발전시킨다. 구현 전환 기준을 두고 기획에 필요한 제한된 기술 검증은 해당 범위로 구분한다.

## D-002 실제 사용 화면을 그리며 발전시킨다

**사용자 방향:** “개발자도 눈에 보이는게 있어야 하고 사용자 입장에서도 화면이 가장 중요하니까, 실제 사용 화면을 그림으로 그려가면서 발전시켜나가는게 중요할것 같아.”

**적용:** 첫 핵심 과업부터 실제 화면으로 표현한다. 화면을 보며 의도·동작·상태를 확인하고 버전과 수정 이유를 기록한다.

## D-003 실무 방법론과 공개 지침을 근거로 삼는다

**사용자 요청:** 일반론을 넘어 개발 기획의 참고 자료, 의도를 상세히 전달할 인터뷰 스킬, 실무자 노하우를 조사한다.

**적용 제안:** Working Backwards, Shape Up, User Story Mapping, 요구사항 공학, 이야기 중심 인터뷰, ACTA, Example Mapping, 문서 작성 방법을 목적별로 조합한다. 공개 에이전트 워크플로는 원문을 확인해 필요한 부분을 채택한다.

## D-004 첫 스킬의 형태

**저장소 제안:** 외부 프레임워크 전체에 의존하지 않는 `visual-product-planning` 스킬, 양식, 가상의 화면 예제를 먼저 둔다.

**판단 조건:** 실제 프로젝트에서 질문 부담·의도 누락·화면과 문서의 불일치를 확인해 수정한다. 현재 스킬과 예제는 실제 사용자 조사로 검증되기 전의 초안이다.

## D-005 원문을 운영 기준과 증거로 연결한다

근거일: 2026-11-14.

**사용자 요청:** “핵심 원문을 더 깊이 조사하고 화면 품질 평가와 사용자 테스트 기준까지 보강해서 ProductPlanning의 스킬과 지침에 반영해줘.”

**적용:** 실제 읽은 원문의 절, 추출한 원칙, 반영한 파일을 연결한다. WCAG 규범·해설, 전문가 휴리스틱, 저장소의 운영 제안을 구분한다. 화면의 문제 심각도와 근거 수준을 따로 기록한다.

**검증 범위:** 기존 화면을 다시 렌더링해 자체 평가하고 사용자 테스트 계획을 작성한다. 실제 참가자가 없는 계획과 모의 사례를 실제 관찰이나 스킬의 효과 검증으로 표현하지 않는다.
