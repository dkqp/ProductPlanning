# 화면을 보며 제품 기획을 발전시키는 흐름

기획의 단위는 사용자가 끝내려는 한 가지 과업이다. 해당 과업의 의도·화면·동작·가이드·검증 결과를 함께 발전시킨다. 핵심 과업에서 제품의 성격을 확인한 뒤 범위를 넓힌다.

## 1. 의도와 현재 상황을 파악한다

왜 만들고 싶은지, 누구의 어떤 상황을 바꾸려는지, 무엇을 성공과 실패로 보는지 묻는다. 실제 사례나 기존 작업물을 함께 본다. [인터뷰 지침](../.agents/skills/visual-product-planning/references/interview.md)을 질문 은행으로 사용한다.

[기획서](../.agents/skills/visual-product-planning/assets/templates/planning-brief.md)의 짧은 초안을 만든다. 사용자의 의사와 실제 사용자 행동에 대한 근거는 따로 기록한다.

## 2. 첫 과업을 실제 화면으로 그린다

첫 화면에 들어오는 이유, 보이는 정보, 누르는 행동, 다음 화면과 완료 결과를 연결한다. 첫 시안은 보통 1~3개 화면으로 시작할 수 있으며 필요한 수는 조정한다.

SVG·디자인 프레임·이미지·실행 화면으로 실제 화면 구성을 보여 준다. 실제 문구·예시 데이터·주요 행동·현재 상태를 드러낸다. 흐름도는 화면 사이의 관계를 보조한다.

## 3. 화면을 따라 인터뷰하고 바꾼다

‘여기서 무엇을 하겠는가’, ‘이 행동 뒤 무엇이 나타나야 하는가’를 확인한다. 기획자와 목표 경험을 합의하는 검토, 실제 사용자의 사용성 검증을 구분한다.

답변을 반영해 화면과 [명세](../.agents/skills/visual-product-planning/assets/templates/screen-spec.md)를 함께 고친다. 버전·변경 이유·남은 질문을 연결한다. 중요한 경우 선택하지 않은 안의 이유도 남긴다.

## 4. 가이드를 먼저 따라 해 본다

[사용자 가이드](../.agents/skills/visual-product-planning/assets/templates/user-guide.md)를 실제 과업 순서로 쓴다. 문구와 순서가 화면에 맞는지, 결과를 확인하고 실패에서 이어갈 수 있는지 본다.

설명이 길어지는 부분은 화면 개선 후보로 기록한다. 안내가 필요한 업무 지식과 화면 자체의 혼란을 구분해 검토한다.

## 5. 예외와 핵심 가설을 확인한다

[Example Mapping](research/2026-11-08-methods.md#example-mapping)처럼 규칙·구체적 사례·미정 질문을 나눈다. 해당 과업에 영향을 주는 실패·빈 화면·기다림·권한·데이터 변화를 확인한다. 동작이 크게 달라지는 상태를 먼저 그린다.

기술 제약이 화면의 약속을 바꿀 수 있으면 범위를 정한 작은 실험을 제안한다. 결과는 화면과 기획에 반영한다. 시연용 모의 응답과 실제 연동 결과를 구분한다.

## 6. 구현 전환을 판단한다

[검토와 전환 양식](../.agents/skills/visual-product-planning/assets/templates/review-and-handoff.md)에 현재 버전과 근거를 남긴다.

- 핵심 과업을 시안에서 처음부터 끝까지 설명하고 수행할 수 있다.
- 기획서·화면·가이드의 용어와 동작이 일치한다.
- 결과가 달라지는 중요한 규칙과 예외가 정해져 있다.
- 사용성 검증의 범위·결과와 아직 확인하지 못한 가설이 드러나 있다.
- 기술 위험의 결과 또는 구체적 확인 계획과 이번 구현 범위가 있다.
- 사용자가 해당 범위의 실제 구현으로 전환할 의사를 확인했다.

이미 승인된 범위의 문서 정리와 시안 수정마다 재승인을 요구하지 않는다. 영향이 작고 처리 방안이 분명한 미정 사항은 기록하고 다음 단계로 갈 수 있다.

## 구현에 넘길 묶음

최신 기획서, 화면 원본과 미리보기, 화면·상태·규칙 명세, 과업별 가이드, 검토 기록과 미해결 질문을 넘긴다. 사용자 발언에서 규칙·화면·완료 기준까지 연결되는 짧은 대응표를 포함한다.

구현 중 새 제약이 사용자 경험을 바꾸면 관련 화면과 가이드도 갱신한다.
