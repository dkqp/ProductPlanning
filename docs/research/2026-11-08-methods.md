# 소프트웨어 제품 기획 방법론과 출처 조사

확인일: **2026-11-08**.

## 질문과 결론

기획자의 의도를 상세히 끌어내고 실제 사용 화면과 사용자 가이드를 먼저 발전시킨 뒤 코딩 에이전트에 구현을 맡기려면 어떤 실무 자료를 참고할 수 있는가?

**적용 제안:** 제품의 약속은 Working Backwards, 범위와 위험은 Shape Up, 사용자 흐름은 User Story Mapping, 상세 동작은 Example Mapping과 요구사항 공학으로 구체화한다. 기획자 인터뷰와 고객의 과거 행동 인터뷰는 목적을 구분한다. 전문가의 암묵적인 판단에는 ACTA를 참고한다. 화면 시안과 가이드는 이 판단을 함께 검토할 자료로 사용한다.

도서는 저자·출판사의 공개 설명과 목차를 확인했고, 공개 방법론·에이전트 지침은 아래 원문을 확인했다. 도서 전체 독서와 도구 실행 성능 비교는 수행하지 않았다.

## 목적별 참고 자료

### Working Backwards

**저자와 자료:** Colin Bryar, Bill Carr. [PR/FAQ 설명과 양식](https://workingbackwards.com/resources/working-backwards-pr-faq/).

**확인한 내용:** 만들기 전에 목표 고객 경험을 설명하는 보도자료와 FAQ를 작성한다. 고객용 FAQ와 내부 FAQ를 구분하고 반복 토론으로 구체화한다. 내부 질문에는 실현 조건과 위험도 포함한다.

**적용:** 보고서 앞부분에 사용자가 얻을 변화와 시작 방법을 쓴다. 가상 고객 발언은 창작임을 표시하고 실제 인터뷰 인용과 구분한다. 문서의 설득력과 고객 수요의 증거를 구분한다.

### Shape Up

**저자와 자료:** Ryan Singer. [공개 책](https://basecamp.com/shapeup), [Find the Elements](https://basecamp.com/shapeup/1.3-chapter-04), [Write the Pitch](https://basecamp.com/shapeup/1.5-chapter-06).

**확인한 내용:** Pitch는 문제, 투입할 시간의 한도인 appetite, 해법, 깊이 빠질 위험인 rabbit holes, 제외 범위인 no-gos를 담는다. Breadboard와 fat marker sketch로 해법의 요소와 관계를 표현한다.

**적용:** 문제와 이번 범위를 화면 옆에 남긴다. 초기 화면은 중요한 구조와 행동을 판단할 정도로 그린다. 여섯 주 주기 등 전체 운영 방식은 별도 도입 판단이다.

### User Story Mapping

**저자와 자료:** Jeff Patton. [저자의 자료 모음](https://jpattonassociates.com/story-mapping/).

**확인한 내용:** 사용자 여정을 이야기하며 함께 지도를 만드는 방법이다. 저자는 책·원문 글·강의·빠른 참조 자료를 제공한다.

**적용:** 사용자가 시작하고 행동하고 끝내는 과정을 연결하고 화면과 가이드를 대응시킨다. 지도와 실제 화면의 이해를 각각 확인한다.

### Software Requirements 3rd Edition

**저자와 자료:** Karl Wiegers, Joy Beatty. [출판사 설명과 목차](https://www.microsoftpressstore.com/store/software-requirements-9780735679665).

**확인한 내용:** 요구사항 도출·문서화·품질·데이터·비기능 요구사항·프로토타입·검증·변경 관리를 다룬다. 목차에서 관련 항목을 확인했다.

**적용:** 상세 명세와 검토의 참고서로 사용한다. 먼저 볼 부분은 7장 도출, 11장 좋은 요구사항, 14장 기능 외 품질, 15장 프로토타입, 17장 검증이다. 목차에 따른 읽기 제안이다.

### 고객 인터뷰

**저자와 자료:** Rob Fitzpatrick의 [The Mom Test](https://www.momtestbook.com/), Teresa Torres의 [Customer Interviews](https://www.producttalk.org/customer-interviews/).

**확인한 내용:** The Mom Test는 편향된 피드백을 피하고 고객 대화에서 근거를 얻는 실무 안내서다. Torres는 특정 과거 행동의 이야기를 요청하고 발견한 기회를 snapshot으로 정리하는 방법을 설명한다. 사용성 테스트와 고객의 목표·상황을 배우는 인터뷰도 구분한다.

**적용:** 실제 사용자에게는 최근 경험과 당시의 행동을 묻는다. 기획자가 원하는 목표 경험은 따로 기록한다. 에이전트의 고객 역할극은 질문과 가설을 만드는 연습으로 다룬다.

### ACTA

**저자와 자료:** Laura G. Militello, Robert J. B. Hutton. 1998. [논문 DOI](https://doi.org/10.1080/001401398186108), [확인한 논문 사본](https://assets.super.so/0ace7157-3bf6-491e-a8e0-fe9e6715c2db/files/eb1e3fa9-c697-4632-b91c-ef28a428466c.pdf), [미 연방철도청의 CTA 설명](https://railroads.dot.gov/human-factors/elearning-attention/cognitive-task-analysis).

**확인한 내용:** 과업 다이어그램, knowledge audit, 시나리오 기반 인터뷰로 전문가의 인지적 요구를 끌어낸다. 구체적 상황의 단서·전략·초보자가 어려워하는 판단을 묻고 결과를 종합한다. 논문 1620~1623쪽의 방법 설명을 확인했다.

**적용 제안:** 업무를 잘 아는 기획자가 당연하게 여기는 판단 규칙에 활용한다. 현재 사례의 회고와 미래 제품 동작의 선택은 구분한다. 미래 제품의 의도 발견에 ACTA의 실증 결과를 그대로 확장하지 않는다.

### Example Mapping

**저자와 자료:** Matt Wynne. [Introducing Example Mapping](https://cucumber.io/blog/bdd/example-mapping-introduction/).

**확인한 내용:** 스토리 아래 규칙·구체적 예시·미정 질문을 구분해 공통 이해를 만든다. 결과를 모르는 사례는 질문으로 남긴다. 초반부터 정형 테스트 문법에 집중하면 대화의 목적을 놓칠 수 있다고 설명한다.

**적용:** ‘자동으로 저장한다’를 정상·경계·실패 사례로 바꿔 본다. 결정한 사례는 화면 상태·가이드·구현 검증에 연결한다. Cucumber 설치는 필수가 아니다.

### 화면 시안 검증

**자료:** [Google Design Sprint Kit](https://designsprintkit.withgoogle.com/methodology).

**확인한 내용:** Google의 공개 방법은 Understand, Define, Sketch, Decide, Prototype, Validate의 여섯 단계와 목적에 따른 방법 선택을 안내한다. 개요는 검색에 노출된 공식 본문으로 확인했으며 동적 페이지 전체는 열람 도구에서 추출되지 않았다.

**적용:** 중요한 경험을 시안으로 표현하고 목표 사용자와 확인하는 기법 모음으로 참고한다. 시안 검증을 실제 서비스 성능이나 사업성의 확인으로 확대하지 않는다.

### 사용자 가이드를 먼저 쓰기

**저자와 자료:** Tom Preston-Werner의 [Readme Driven Development](https://tom.preston-werner.com/2010/08/23/readme-driven-development.html), Daniele Procida의 [Diátaxis](https://diataxis.fr/).

**확인한 내용:** 전자는 코딩 전에 README를 작성해 사용법과 인터페이스를 구체화할 것을 제안한다. 후자는 문서의 목적을 tutorial, how-to guide, reference, explanation으로 구분한다.

**적용:** 첫 성공 경험을 따라 하는 짧은 가이드와 과업별 안내를 우선한다. 정책·항목 설명과 설계 이유는 필요할 때 나눈다. README 선행 작성은 저자의 실무 제안으로 다룬다.

## 인터뷰에 대한 적용 판단

1. 기획자의 의도는 원하는 변화와 판단 기준을 열린 질문으로 듣는다. 선택지를 너무 먼저 제시하면 의도를 좁힐 수 있다.
2. 업무 전문가는 실제 사건·판단 단서·예외·초보자의 실수를 파고든다.
3. 실제 고객은 특정 과거 행동을 묻는다. 미래 사용 의향만으로 수요를 확인하지 않는다.
4. 화면 동작을 결정할 때는 대안과 구체적 사례를 보여 주고 차이를 확인한다.

위 항목은 자료들을 현재 목적에 맞게 조합한 제안이다.

## 다음 실험과 미해결 질문

- 실제 프로젝트의 핵심 과업 하나로 인터뷰 → 화면 → 가이드 → 재검토를 실행한다.
- 바로잡은 오해, 화면을 본 뒤 바뀐 결정, 구현 전에 발견한 규칙을 기록한다.
- 질문의 충분함은 ‘다른 구현자가 같은 경험을 이해할 수 있는가’로 판단한다.
- 대상 사용자·제품 분야·화면 제작 도구·문서 깊이는 프로젝트마다 정한다.
