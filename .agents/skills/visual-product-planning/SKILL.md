# 실제 사용 화면으로 구체화하는 제품 기획

기획자·개발자·사용자가 함께 판단할 화면을 만들고 의도·동작·상태를 기획서와 가이드에 연결한다. 기존 자료와 결정, 대상 프로젝트 지침을 먼저 읽고 필요한 부분부터 진행한다.

## 의도를 확인하고 첫 과업을 고른다

- 의도와 판단이 모호하면 [인터뷰 지침](references/interview.md)을 읽는다. 왜 만들고 싶은지 열린 질문으로 듣고 중요한 미정 사항부터 묻는다. 기존 답을 되묻지 않는다.
- 기획자 목표, 실제 사용자 관찰, 에이전트 제안과 가정을 구분한다. 실제 사용자 인터뷰는 특정 과거 사건을 듣는 별도 활동이다.
- 제품의 성격을 드러내는 핵심 과업 하나로 시작한다. 자료가 충분하면 첫 화면과 해석을 제시해 확인한다.
- 역할·시작 사건·전제·완료 조건·정상 흐름·대안·예외를 필요한 깊이로 적는다. 규칙·사례·미정 질문을 나누고 발언→결정→화면→검증을 연결한다. 결정되지 않은 예시의 결과를 임의로 확정하지 않는다.

## 화면을 그려서 대화를 이어 간다

- [화면 검토 지침](references/screen-loop.md)을 읽고 실제 화면 형태의 그림과 편집 가능한 원본을 만든다. SVG·디자인 프레임·이미지·실행 화면 중 사용할 수 있는 표현을 고른다.
- 실제 문구와 가상임이 표시된 예시 데이터, 주요 행동과 결과를 넣는다. 흐름도나 화면 목록만으로 시안을 완료했다고 하지 않는다.
- 화면에서 무엇을 하고 무엇을 기대하는지 확인한다. 사용자 답과 자신이 채운 가정을 구분해 되돌려 설명하고 중요한 오해를 먼저 수정한다.
- 답이 동작을 바꾸는 부분은 대안이나 구체적 예시로 묻는다. 작은 제작 선택은 이유를 붙여 제안한다. 버전과 변경 이유를 남긴다.
- 정적인 그림으로 판단하기 어려울 때 범위를 정한 클릭 시안을 추가한다. 모의 응답·실제 연동·동작하지 않는 부분을 구분한다.

## 문서와 검증을 함께 갱신한다

양식을 필요에 맞게 조정한다. 같은 목적의 문서가 있으면 기존 형식을 따른다.

- [기획서](assets/templates/planning-brief.md): 원하는 변화, 근거, 범위, 성공과 실패 기준.
- [화면 명세](assets/templates/screen-spec.md): 과업, 정보, 행동, 상태와 규칙, 미정 사항.
- [사용자 가이드](assets/templates/user-guide.md): 시작 조건, 순서, 결과 확인과 복구.
- [검토와 전환](assets/templates/review-and-handoff.md): 검토한 버전과 근거, 남은 위험과 결정.

규칙을 정상·경계·실패 사례로 확인한다. 결과를 모르는 사례는 질문으로 남긴다. 문서와 화면의 용어·동작을 맞추고 중요한 변경의 영향을 함께 점검한다.

## 화면의 품질을 평가한다

화면이 생기면 [화면 품질 지침](references/screen-quality.md)과 [평가 양식](assets/templates/screen-quality-review.md)을 사용한다. 현재 버전의 화면을 직접 보고 과업·정보·행동·복구와 관련 접근성 항목을 검토한다. 문제마다 위치·영향·근거·수정·재검증을 연결한다.

판정은 확인·문제·미확인·해당 없음으로 나눈다. 심각도와 근거 수준은 따로 기록하고 총점으로 통과시키지 않는다. 정적 화면에서 키보드·클릭 영역·보조기술·실제 저장을 확인했다고 하지 않는다. 계산한 대비나 선택한 WCAG 항목을 전체 접근성 준수로 보고하지 않는다.

## 사용자 테스트를 준비하고 기록한다

실제 사용자 검증을 계획하거나 진행할 때만 [사용자 테스트 지침](references/user-testing.md)과 [양식](assets/templates/usability-test.md)을 읽는다. 연구 질문·대상·버전·중립적인 과업·완료 조건·도움/중단 규칙을 정한다. 모집이나 연락은 별도로 허용된 범위에서 진행한다.

실제 관찰과 해석·제안을 나누고 독립 완료·도움 후 완료·미완료·미실행을 구분한다. 자체 평가·역할극·파일럿을 대상 사용자 결과에 합산하지 않는다. 세션이 없으면 계획과 미검증 항목을 전달하며 결과를 만들지 않는다.

## 구현으로 넘긴다

핵심 경험의 검토 결과, 남은 가설과 기술 위험, 구현 범위를 정리해 사용자의 전환 의사를 확인한다. 이미 승인된 범위를 다시 묻지 않는다. 시안 제작 허용을 제품 전체 구현의 승인으로 확대하지 않는다.

핵심 과업의 치명적인 문제나 중요한 미확인은 해결·범위 변경·명시적인 위험 처리로 남긴다. 실제 사용자 검증이 없으면 해당 근거를 미검증으로 표시하고 필요한 다음 확인과 전환 판단을 구분한다.

최신 화면과 원본, 관련 문서, 바뀐 결정과 검증하지 못한 부분을 연결해 전달한다. 실제 사용자 조사·서비스 동작·성능·접근성은 수행한 범위의 증거로만 보고한다. 이미지의 정교함을 기능 검증으로 보고하지 않는다.
