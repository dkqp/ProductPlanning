# 의도와 판단 기준을 끌어내는 인터뷰

## 목적을 구분한다

| 인터뷰 | 알아낼 것 | 질문의 중심 |
|---|---|---|
| 기획자 | 이유, 원하는 변화, 양보할 수 없는 기준 | 목표·실패·우선순위·구체적 장면 |
| 업무 전문가 | 생략되는 단서·판단·예외 | 실제 사례와 어려운 판단의 회고 |
| 실제 사용자 | 현재 행동·문제·대안·비용 | 특정 과거 사건 |
| 화면 동작 결정 | 규칙·경계·예상 결과 | 시안의 구체적 사례 |

의도가 분명해졌다고 고객 문제가 검증된 것은 아니다. 같은 사람이 역할을 겸하면 어떤 역할의 답인지 표시한다.

## 질문을 운영한다

자료와 기존 답을 읽는다. 처음에는 사용자 자신의 언어로 의도를 설명하게 한다. 기본적으로 중요한 질문 하나씩 묻고 사용자가 일괄 답변을 원하면 관련 질문을 짧게 묶는다.

결과에 미치는 영향과 불확실성이 큰 질문을 고른다. 작은 스타일 선택은 이유를 붙여 제안한다. 의도를 알게 된 뒤 대안과 장단점을 보여 줄 수 있다. 고객의 행동 근거를 수집할 때는 추천 답을 먼저 주지 않는다.

## 기획자 질문 은행

- 꼭 만들고 싶게 한 구체적인 장면은 무엇인가?
- 그 장면에서 누가 무엇을 하고, 무엇이 달라졌으면 하는가?
- 기능이 동작해도 어떤 모습이면 실패라고 느끼겠는가?
- 속도·정확도·사용자의 통제가 충돌하면 무엇을 지켜야 하는가? 실제 사례에서는 어떻게 판단하는가?
- 처음 들어온 사용자가 가장 먼저 해내길 원하는 일은 무엇인가?
- 참고 제품에서 가져오거나 피하고 싶은 점은 어떤 화면·동작인가?

‘간단하게’, ‘자동으로’, ‘똑똑하게’의 의미를 확인한다. ‘자동으로’가 추천, 실행 후 취소, 확인 없는 확정 중 어느 경험인지 실제 장면으로 묻는다.

## 전문가의 판단을 알아낸다

현재 과업을 큰 단계로 나누고 판단이 어려운 곳을 고른다. ACTA를 참고해 다음을 묻는다.

- 최근 경험이 중요한 차이를 만든 사례를 처음부터 설명해 줄 수 있는가?
- 어떤 단서를 보고 다음 행동을 결정했는가?
- 같은 입력처럼 보여도 다르게 처리한 사례는 무엇인가?
- 경험이 적은 사람은 어디서 어떤 실수를 하는가?
- 평소 규칙을 적용하지 않은 예외는 무엇이며 왜 예외였는가?

현재 사례의 회고와 미래 동작의 선택을 구분한다. 기억만으로 확인하기 어려우면 샘플 자료나 업무 흔적을 요청하되 제공할 수 없는 자료를 필수 조건으로 만들지 않는다.

## 화면으로 이해를 확인한다

‘AI가 알아서 정리해 주면 좋겠다’에 대해 초안을 만든 뒤 사용자 확인, 자동 확정 후 수정, 근거 부족 항목만 질문은 서로 다른 제안이다. 먼저 이유를 듣고 화면을 그려 차이를 보여 준다. 선택지를 사용자가 처음부터 원했던 요구사항으로 기록하지 않는다.

‘이해한 목표’, ‘보일 화면’, ‘에이전트 제안’, ‘미정’을 짧게 되돌려 설명한다. 화면의 특정 행동이나 사례를 지목해 확인한다.

## 구체적 사건을 따라가는 후속 질문

고객의 현재 문제를 배울 때는 최근에 기억나는 사건 하나를 고른다. 시작 계기 → 당시 상황과 도구 → 실제 행동 → 판단 단서 → 우회 방법 → 결과의 순서로 필요한 빈틈을 확인한다. 일반적인 선호나 미래 사용 의향만으로 현재 행동을 확인했다고 하지 않는다.

‘그다음에는 무엇을 하셨나요?’, ‘그때 무엇을 보고 판단하셨나요?’, ‘실제로 남은 자료가 있나요?’처럼 앞선 답에 이어 묻는다. 기억나지 않거나 실제 근거가 없으면 그 상태로 남긴다. 기획자의 미래 경험을 선택하는 질문에는 제안과 대안을 쓸 수 있지만, 이를 고객이 과거에 했던 행동으로 바꾸어 기록하지 않는다.

전문가 인터뷰에서는 큰 단계의 지도를 먼저 만들고 어려운 판단을 고른다. 실제 사건의 단서·선택지·전략·초보자가 하기 쉬운 실수를 연결한다. 모든 사고 과정을 한 번에 설명하게 하기보다 다음 설계에 영향을 주는 판단을 구체화한다.

## 답을 과업과 규칙으로 옮긴다

역할, 시작 사건, 시작 전 조건, 완료 후 조건, 정상 흐름, 대안과 실패를 필요한 깊이로 적는다. ‘빠르게·편리하게’는 관찰할 상황과 결과로 구체화한다. 지연 시간 등 수치가 필요하면 목표와 측정 조건의 근거를 확인하고 에이전트 제안은 가정으로 표시한다.

사용자의 화면 조작에 드러나지 않는 만료·외부 데이터 변경·예약 처리도 화면의 약속을 바꾸는지 확인한다. 화면을 중심으로 논의하더라도 사용 흐름에 나온 요구만으로 전체 요구가 완성됐다고 판단하지 않는다.

규칙을 요약하는 문장, 그 규칙을 설명하는 사례, 아직 결과를 결정하지 못한 질문을 구분한다. 예를 들어 ‘미확인 1건이면 완료할 수 없다’는 규칙이 가정이면 사용자 결정으로 승격시키지 않는다. 완료 조건과 화면 상태, 가이드, 나중에 확인할 사례를 같은 식별자로 연결한다.

| 부족한 진행 | 개선한 진행 |
|---|---|
| ‘자동 확정 기능이 필요한 거죠?’ | 먼저 원하는 변화와 구체적인 상황을 듣고 확인·실행·취소의 권한을 분리해 화면으로 보여 준다. |
| ‘보고서 기능이 필요하다’만 기록 | 누가 무엇을 계기로 시작해 어떤 결과를 얻는지, 실패하면 어떻게 이어가는지를 정리한다. |
| 미정 사례의 결과를 에이전트가 채움 | 결정을 바꾸는 질문으로 남기고 결정권자·영향·다음 확인을 연결한다. |

## 기록

| 발언 또는 관찰 | 해석 | 제안 / 사용자 결정 / 미정 | 연결한 화면·규칙 | 다음 확인 |
|---|---|---|---|---|

질문을 계속 늘리기보다 핵심 과업의 화면과 행동을 설명할 수 있으면 시안을 제시한다. 새로 생긴 중요한 모호함은 화면 검토에서 다룬다.
