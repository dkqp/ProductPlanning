# 사용자 테스트의 계획과 판정

화면을 그린 뒤 기획자와 합의하는 활동, 전문가의 자체 평가, 실제 사용자의 과업 수행은 서로 다른 근거다. 이 지침은 실제 사용자 세션을 준비하고 기록할 때 사용한다. [테스트 양식](../assets/templates/usability-test.md)을 필요한 깊이로 채운다.

## 1. 무엇을 배울지 먼저 정한다

연구 질문·사용자 유형·과업·화면 버전·기기·구현 범위를 정한다. 요구사항의 완료 조건과 사용성의 성공 조건을 구분한다. 세션 결과를 본 뒤 유리하게 성공 조건을 바꾸지 않는다. 변경하면 이유와 버전을 남긴다.

실제 또는 잠재 사용자를 고르고 업무 경험·초보 여부·접근성 요구 등 중요한 차이를 포함한다. 표본 수와 모집 방법의 이유를 적고, 특정 인원을 모든 제품의 충분성 기준으로 고정하지 않는다. 동료 파일럿은 질문과 환경 점검이며 대상 사용자 결과에 합산하지 않는다. 에이전트 역할극은 사전 연습으로 표시한다.

## 2. 중립적인 과업을 만든다

각 과업에 사용자에게 읽어 줄 문장, 시작 조건, 평가자용 완료 조건, 관찰할 질문, 시안의 제약, 도움·중단 규칙을 적는다. 목표를 주되 버튼 이름과 정답 경로를 미리 알려 주지 않는다. 업무 경험에 맞는 현실적인 맥락을 사용한다.

가이드와 제품 내 도움을 사용할 수 있는지 미리 정한다. 허용된 제품 내 도움의 사용과 진행자의 경로 힌트는 구분한다.

| 부족한 지시 | 개선한 지시 | 평가자만 보는 조건 |
|---|---|---|
| ‘출처 보기와 확인 표시를 누르세요’ | ‘이 초안을 검토해, 검토를 마친 상태로 남겨 주세요’ | 근거를 열고 판단한 뒤 완료 상태를 확인하는가? |
| ‘나중에 검토 버튼을 찾으세요’ | ‘지금 자료를 열 수 없습니다. 하던 일을 잃지 않고 나중에 이어가려면 어떻게 하시겠어요?’ | 초안 유지와 재진입 방법을 이해하는가? |

가상 데이터는 현실감 있게 만들되 실제 근거와 구분한다. 정적 화면을 진행자가 교체하는 방식이라면 교체 규칙을 고정한다. 그림에서 할 수 없는 동작을 못 했다는 이유로 사용자를 실패로 판정하지 않는다.

## 3. 세션을 준비하고 진행한다

안내문에는 목적, 사용자를 평가하는 시험이 아니라는 점, 중단 가능 여부, 기록과 이용 범위를 담는다. 동의 범위를 확인하고 필요한 기록만 수집한다. 공개 저장소에는 이름·연락처·원본 녹화 등 식별 정보를 올리지 않는다. 샘플에는 익명 코드와 가상 데이터를 쓴다.

먼저 파일럿으로 문장·순서·작동 범위를 확인한다. 본 세션에서는 중립적으로 과업을 제시하고 관찰한다. 생각을 말해 달라고 요청할 수 있다. 막히는 즉시 답을 알려 주지 않는다. 개입이 필요하면 시점과 내용을 기록하고 이후 결과를 독립 성공과 구분한다.

‘어떤 점이 그렇게 느껴지게 했나요?’처럼 열린 후속 질문을 쓴다. 호감·사용 의향·자가 보고는 과업 성공의 대체 지표가 아니다. 불편·피로·동의 철회 또는 사전에 정한 조건에 이르면 중단한다.

## 4. 관찰을 기록한다

| 결과 | 기록 기준 |
|---|---|
| 독립 완료 | 정한 시작·완료 조건을 경로 힌트 없이 충족 |
| 도움 후 완료 | 경로·정답에 영향을 주는 개입 뒤 충족. 도움 내용을 함께 기록 |
| 미완료 | 수행했지만 완료 조건을 충족하지 못함. 원인을 추정과 구분 |
| 미실행·판정 불가 | 시안 제한·환경 문제·중단 등으로 결과를 판정할 수 없음 |

이는 저장소의 운영 분류다. 소요 시간은 시작·끝·일시 중지 정의와 환경을 함께 기록한다. 정적 시안에서 진행자가 화면을 바꾸는 시간은 실제 제품 성능으로 해석하지 않는다. 비율을 쓰면 분자·분모와 제외 이유를 적고 작은 표본을 시장 전체로 일반화하지 않는다.

관찰에는 보거나 들은 한 가지 사실을 적는다. 해석과 설계 변경은 다른 칸에 둔다. 예: ‘P01이 비활성 버튼을 두 번 선택하려 함’은 관찰, ‘완료 조건이 불명확할 수 있음’은 해석, ‘확인 조건을 버튼 위에 표시’는 제안이다. 이 예시는 기록법 설명을 위한 창작이며 실제 세션 결과가 아니다.

## 5. 다음 결정을 내린다

관찰을 과업·단계·사용자 유형별로 묶고 발견을 정리한다. 반대 사례와 해석의 다른 가능성도 남긴다. 문제는 [화면 품질 지침](screen-quality.md)의 영향과 근거 수준으로 정리한다.

치명적인 차단·데이터 손실·중요한 오해는 해당 범위의 수정·재검증 또는 범위 변경으로 처리한다. 중요한 문제에는 조치·담당·재검증 과업을 남긴다. 미실행된 핵심 과업이나 중요한 미확인 항목을 통과로 바꾸지 않는다. 위험을 수용할 경우 결정권자·이유·확인 계획을 적고 이미 승인된 범위를 불필요하게 재승인받지 않는다.

인터뷰 → 화면 → 가이드로 돌아갈 항목을 정하고 수정 버전에서 같은 완료 조건을 다시 확인한다. 사용성 점검만으로 수요·사업성·실서비스 성능이 증명됐다고 하지 않는다.
